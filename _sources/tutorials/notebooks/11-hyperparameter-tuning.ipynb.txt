    "## 2. What gets tuned: the search space\n",
    "\n",
    "Every Twiga model config carries a `search_space` field of type `BaseSearchSpace`.\n",
    "This object declares which parameters Optuna is allowed to sample, and within what\n",
    "ranges or from what categorical lists.\n",
    "\n",
    "**Fixed parameters** are set directly on the config object and are never changed by\n",
    "the optimizer (e.g. `boosting_type`, `objective`, `metric`, `verbose`).\n",
    "\n",
    "**Tunable parameters** are declared inside `search_space`. When `tune()` is called\n",
    "the `get_optuna_params(trial)` method merges both: fixed values form the baseline,\n",
    "and any key present in the search space overrides that baseline with a value sampled\n",
    "by the Optuna trial."
   ]
  },
  {
   "cell_type": "markdown",
   "id": "9",
   "metadata": {},
   "source": [
    "> **Key concept - Bayesian optimisation**\n",
    ">\n",
    "> Random search and grid search evaluate hyperparameter configurations independently - \n",
    "> each trial ignores the outcomes of previous ones. This is wasteful when training is\n",
    "> expensive.\n",
    ">\n",
    "> Optuna's **TPE (Tree-structured Parzen Estimator)** sampler builds a probabilistic\n",
    "> surrogate model of the objective function from all previously evaluated trials. It\n",
    "> then proposes the next configuration in a region where the surrogate predicts a good\n",
    "> outcome - effectively learning *where* in the search space to look next.\n",
    ">\n",
    "> A **trial** is one complete evaluation of the objective: sample a config → train the\n",
    "> model on CV folds → report the mean validation RMSE → store the result. After ~20\n",
    "> trials the surrogate is warm enough to focus exploration on promising regions,\n",
    "> outperforming random search for the same compute budget."
   ]

    "> **Key concept - search space definition**\n",
    ">\n",
    "> Twiga's `BaseSearchSpace` maps parameter names to their sampling specifications:\n",
    ">\n",
    "> - **Categorical** - a Python list, e.g. `linear_tree=[True, False]`. Optuna uses\n",
    ">   `trial.suggest_categorical()` and can select any element.\n",
    "> - **Integer range** - a `(low, high)` tuple of integers, e.g. `num_leaves=(16, 256)`.\n",
    ">   Sampled with `trial.suggest_int(low, high)`.\n",
    "> - **Float range** - a `(low, high)` tuple of floats, e.g. `learning_rate=(0.001, 0.3)`.\n",
    ">   Log-scale sampling is applied automatically when `low > 0` and the ratio\n",
    ">   `high / low > 5`, which is appropriate for learning rates and regularisation strengths.\n",
    ">\n",
    "> **Fixed parameters** - anything set directly on the config object (`boosting_type`,\n",
    "> `objective`, `metric`, `verbose`) bypasses the search space entirely and is passed\n",
    "> unchanged to the model. This lets you freeze architectural choices while tuning only\n",
    "> numerical knobs."

    "> **Key concept - overfitting HPO**\n",
    ">\n",
    "> A common mistake is to run HPO and evaluate on the **same test set** you use to\n",
    "> report final metrics. This leaks information: you are effectively choosing the\n",
    "> hyperparameters that happen to work best on that particular test period, not\n",
    "> hyperparameters that generalise.\n",
    ">\n",
    "> The correct protocol has three non-overlapping splits:\n",
    ">\n",
    "> | Split | Used for |\n",
    "> |-------|----------|\n",
    "> | **Train** | Model fitting during each trial |\n",
    "> | **Validation** | Optuna objective - the RMSE reported per trial |\n",
    "> | **Test** | Final honest evaluation, never seen during HPO |\n",
    ">\n",
    "> In Twiga, `forecaster.tune(train_df, val_df, ...)` uses the validation set as the\n",
    "> HPO objective, leaving `test_df` untouched until the very end. This is the same\n",
    "> reason `ExperimentConfig` distinguishes `train_size` from `test_size` - the test\n",
    "> folds are reserved and never influence the surrogate model."
   ]

    "## 7. Study persistence: resuming a study\n",
    "\n",
    "Optuna stores every trial in a SQLite database located at\n",
    "`studies/<project_name>.db`. This means:\n",
    "\n",
    "- You can **interrupt a run** (Ctrl-C, kernel restart, VM shutdown) at any point\n",
    "  without losing progress.\n",
    "- To **resume**, simply construct `ExperimentConfig` with the **same `project_name`**\n",
    "  and call `tune()` again. Optuna will reopen the existing study, load all\n",
    "  previously evaluated trials, and continue sampling from where it left off.\n",
    "- The TPE surrogate is rebuilt from the stored trial history, so later trials\n",
    "  benefit from all the information gathered in earlier runs.\n",
    "\n",
    "This makes it practical to spread a large search (e.g., 200 trials) across\n",
    "multiple notebook sessions or overnight batch jobs without any manual bookkeeping."

    "## 9. Interpreting results: when to tune and when not to\n",
    "\n",
    "### When tuning is worth the cost\n",
    "\n",
    "- **Large datasets with long training folds**: each trial is expensive but the\n",
    "  data provides enough signal to reliably distinguish good from bad configurations.\n",
    "- **Production models**: a one-time tuning investment amortises quickly across\n",
    "  many inference calls.\n",
    "- **Neural network architectures**: the landscape is highly non-convex and\n",
    "  defaults rarely perform well out of the box.\n",
    "\n",
    "### When to skip tuning\n",
    "\n",
    "- **Small datasets (fewer than ~100 samples per fold)**: cross-validation\n",
    "  estimates of the objective are noisy; the optimizer will over-fit to noise\n",
    "  in the fold splits rather than discover genuinely better hyperparameters.\n",
    "- **Time-constrained deployments**: if you need a model in production within\n",
    "  minutes, default tree-model configs are already competitive and tuning adds\n",
    "  latency without a guaranteed payoff.\n",
    "- **Heavily regularised models**: if the model is already underfitting, tuning\n",
    "  hyperparameters without first improving feature engineering will have limited impact.\n",
    "\n",
    "### Trade-off rule of thumb\n",
    "\n",
    "Start with `num_trials=20` for a quick sanity check. If the best trial improves\n",
    "on the default by more than 3 - 5 % on your key metric, extend to 100+ trials.\n",
    "If the improvement is marginal, invest the compute in richer features or a larger\n",
    "ensemble instead."
